## 行为

| 社区夯票占比 | 新规则称呼 |
|---|---|
| 零票 | 待开梁，梁位 `--` |
| 有票且 <25% | 小难梁 |
| 25%–<50% | 梁工 |
| 50%–<70% | 梁总 |
| 70%–<85% | 梁神 |
| 85%–<95% | 梁圣 |
| ≥95% | 梁祖 |

判定与显示使用同一组计数、同一快照及规则版本；六位小数继续截断。
入口、主面板、梁祠、称呼、区间提示、读屏文字和升降音效均覆盖新状态。
香火、夯/拉两种投票和个人进度规则沿用现有实现。

## 版本与历史

- 新规则：`liangzi-v0.2-25-50-70-85-95`。
- 旧规则：`liangzi-v0.1-50-70-85-95`，低于50%均为梁工。
- 已有梁案保留开案规则；新开梁案启用新规则。正常升级后随下一个业务日新案启用，
  显式另开新案也使用新规则；不会仅因重启改变当前案的判定。
- 已封存日/周/月档案按各自记录的规则派生图像和范围提示；不回写旧档案。
- 新封存日梁采用当天最后一案的规则（离线换案绕回时按持久化的最后选中案，不按最大列表下标）；周/月采用最新覆盖日的规则。所有周期先汇总
  原始夯拉票数，再判定称呼；不平均各日比例或等级。临时周期同样保留规则版本。
- 离线聚合增加可选规则版本；缺失版本的旧存储按旧规则读取，已封存档案同时支持
  新旧两版。在线与离线账本、余额、会话结算游标仍按原边界隔离。

## 滚动升级

新 Host 向 Backend 发送 `x-liangxiang-liangzi-policy`，值为新规则版本。
支持新能力的请求得到原始版本化结果；没有声明或无法识别的声明得到旧展示视图：
bootstrap 为四个边界，快照使用旧枚举，history 使用旧规则标识。
转换只发生在响应副本中，票数、快照序列、扣香、幂等票据和数据库行不变。
同一请求先由新客户端投票、再由旧客户端重放，也只扣一次。

新 Host 同时读取四/五边界 bootstrap，并将快照规则版本传到 Client，保证旧服务端
或旧案仍显示一致的范围。封存历史拒绝未知规则；实时响应延续原有过期规则恢复，
避免把已成功的投票当作失败重新发送。

## 图像与构建

`src/client/artwork/nan.png` 来自经确认的草图，保留同一成人梁子脸、眼镜、灰粉卫衣、
小蝴蝶结和缩手姿势。生产图缩到256px并优化调色板，透明 WebP 为28,262字节。
生成脚本直接保留它的 alpha，不转为 JPEG 抠底；七张 WebP 都与各自生产 PNG 的
可见 RGBA 像素逐一比对。原有六张图像没有改变。

客户端压缩空白和内部变量名，显式保留 `module`、`exports`、`require`，关闭表达式
压缩。预算仍为 raw ≤700,000 / gzip ≤400,000 字节；当前为610,849 /395,115字节。
构建门禁执行注册工厂并验证 `apply` / `inject` 导出。安装检查比对实际 combo 与
构建代码，只去掉 DSH `prepareSource` 会删除的调试尾注，避免依赖引号形式。
源码证据：DSH `687f282e86`，`packages/client/modules/src/index.ts`。
