# 香港ECS迁移与验收方案

准备日期：2026-11-08。当前仅完成方案准备；新机初始化、远程测试、数据迁移和切换分别记录结果，不由本文件推定已经执行。

## 目标与边界

- 香港 `ecs.c7a.large`，2 vCPU／4GiB，50GiB ESSD PL0，普通BGP，CDT按流量、10Mbps峰值，先租一个月。
- 正式目标200并发；400只验证短时尽力表现，不要求持续400，也不为此预购更大实例。
- 镜像按最终订单核对。Rocky Linux 10.2是可验证的新机候选；9.8是既有环境基线。不能将“旧版已验”当成“新版不兼容”，也不能将新版正式发布当成梁相已验收。
- 采购截图中的镜像来源、镜像额外费用、SSH凭证、自动续费和CDT启用状态在接入前逐项登记；不从截断的镜像名称推断发布者。
- 当前授权到新机安全准备、网络与独立库验收。公共域名、主服业务、原备份和旧机人工／时间演练环境保持原状。
- 先汇报实测，再由用户决定是否切换；不自动退订旧服务器、释放公网IP或删除旧数据。

## 1. 接入与目标锁定

1. 收到新公网IP、SSH账号及当前端口后，登记实例ID、地域、CPU／内存、主机名、镜像版本和实际架构。
2. SSH初始可能为22；最终使用18800。先验证部署账户公钥登录，再配置18800的sshd、SELinux端口与主机／云防火墙；通过独立的新连接后才关闭22和密码／root远程登录。保留可用会话直到验证结束。
3. 建立 `liangops` 运维账户与独立运行身份；运维授权最小化，应用无root权限。SSH仅允许管理出口；HTTP/S用于证书与代理，内部后端只绑定回环。
4. 新机准备阶段建议使用含 `standby` 段的唯一主机名。目标配置仅保存在本机忽略文件，不提交真实IP、账户、密钥或云实例标识。
5. 控制器、Windows发生器、测试包和健康检查从同一份新目标清单读取地址。启动前校验证书、主机名、环境标签和精确构建号；旧主服、旧备机与公共API域名列入压测拒绝目标。
6. 软件从官方来源安装；记录Node 22具体小版本、pnpm 11.28.5、Caddy及系统包版本。新机内完成更新／必要重启，再开始测试；不在压测期间并行编译或更新。

Rocky 10.2额外核对x86-64-v3暴露特性、Node运行与Ed25519签名、内置SQLite、Caddy／systemd、SELinux与sshd配置。核对实际加密策略；不为通过测试关闭签名、证书校验或SELinux。旧机保持原OS；不做原位跨大版本升级。

## 2. 服务和数据分层

| 环境 | 用途 | 数据与运行约束 |
| --- | --- | --- |
| 现主服 | 继续对外服务 | 原代码、数据库和任务保持运行，不承受压测 |
| 旧备机原实例／人工环境／演练 | 保留原验证现场与回退资产 | 不复用其库、不部署、不重启、不改时钟 |
| 新机候选测试 | 验证梁股和200并发 | 全新合成身份、独立库、独立配置、明确环境标签，限测试出口 |
| 新机生产恢复预演 | 验证原生产版本的数据可恢复 | 一致性副本放隔离目录，只读核对；不开放真实用户写入 |
| 新机未来生产 | 用户决定后接替旧主服 | 原生产同版代码／schema与最终一致数据，唯一写入节点 |

普通迁机与梁股正式发布分开：生产当前已知为1.2.0-u2维护构建，执行前读取真实VERSION／构建文件／schema再锁定；候选梁股的schema14不因迁机自动进入生产。新机候选使用测试前与功能维护者确认的精确提交；不跟随移动中的latest或开发目录。

代码部署继续经 `scripts/deploy.sh` 及对应 `deploy-check.sh`，选定干净、已提交的同版工作树。已有 `internal-test`／`rehearsal` 模式分别管理真实业务时钟和合成时钟的隔离实例；机器不同也必须在清单标明地址和环境。

现有部署脚本是应用部署器，不能直接视为整机迁移／回退工具。正式执行前必须补齐并演练新机引导、同版恢复和回退入口的目标检查；缺少前置环境时停止处理，不伪造健康回执或绕过固定路径护栏，不用手工rsync重启替代受管部署。

## 3. 网络先验收

- 以本机实际公网出口和既有Windows测试出口做两来源实测，记录实际出口位置；不将本机时区当作测源地理位置。
- 增加第三方大陆城市／三网TCP或HTTPS探测，记录真实成功节点和时间；不可获得的节点单列，不用ICMP成功替代应用可用。
- 公网80／443与最终18800分别检查TCP握手、TLS链、HTTP请求、连续SSE、断线重连及SSH传输。记录每来源P50／P95／P99、超时和错误，保留TCP重传／RTO、接收窗口与监听队列观测。
- 新IP使用可被客户端严格验证的TLS方案。Caddy默认IP站点不等于自动取得公有信任证书；先核对实际证书签发能力。必要时使用只指向新机的临时测试子域名，公共主域名保持不动。不得用 `-k` 或全局禁用TLS校验假装通过。
- 基础探测至少连续5分钟，并保留后续测试期间的低频探活。限速测试两来源合计不超过约8Mbps；不让两个发生器各自跑满10Mbps后把人为超额当作线路故障。
- 若再现HTTPS与SSH共同停顿、持续退避或明显超时，立即停止升压、保全采样。仅整理排查结果，不擅改MTU、路由或拥塞算法，更不通过降低行情频率掩盖故障。

CDT按流量的10Mbps是上限，不是带宽保障。网络与容量只能由新机实际结果判断，购买ECS本身不等于前次故障已解决。

## 4. 独立库200并发验收

容量阶段新机仅保留本次必要服务；不额外启动常驻加速演练来消耗CPU，也不停止旧机演练以制造对照。报告分列测试后端、代理、系统和其他进程；注明与前次同机多实例结果的环境差异。

1. 沿用已归档的签名HTTP＋云SSE双来源方法，两边各承担一半身份。所有地址、请求前缀、输出目录和状态文件使用新轮次；不能直接启动带旧地址的控制器。
2. 0用户空载30秒；50、100、150、200各至少60秒，然后200持续至少15分钟。暖机、稳态、首次连接、集中重连分别统计。
3. 覆盖单炷／批量上香、钱包、各盘做多做空、改仓／撤回、Token声明、K线／回执冷读、同ID重试、冲突同ID、断线重连；实际接收全部字段，不只测health或socket握手。
4. 保留每秒更新、全部信息与原精度；不减少更新频率、不关闭部分客户端、不把预期业务拒绝混作传输错误。
5. 记录活跃和近期收到有效帧的身份数、每来源RPC与首帧分位、行情新鲜度、错误、CPU／RSS／可用内存、事件循环、网络字节／Mbps、重传、监听队列和磁盘等待；发生器自身CPU／内存一并记录。
6. 分来源稳态RPC P95以500ms为目标、P99以2秒为目标；非预期请求错误与语义异常为0。95%集中重连在3秒内收到有效首帧、全体在10秒内恢复作为验收目标。超标必须给实际分布与原因，不以合并分位掩盖较慢来源。
7. 若指标介于目标与可用边界之间，单列“待决定”，不伪造通过；未知写入必须核对原意图和正确测试库。结束后所有本轮有记录的待确认意图均有明确入账或规则拒绝结果。
8. 200通过后可做不超过1分钟的400突发观察；单独记录10Mbps上限下的排队与时延，不作为持续400承诺或强制升级依据。

暂按每轮公网出站约1–2GB控制测试规模，执行时以网卡和实际计量核对，不把估算当账单；避免长时间iperf和重复下载大包。实时看板沿用本机入口，明确当前阶段与停止状态，不展示过期值为实时数据。

## 5. 时间推演与账本验收

先完成真实时钟200稳态，再用另一独立合成库／专用演练进程覆盖三批开盘、封盘、定梁、午夜结算、次日、周／月归档及重启。只改该实例的业务时钟，不改服务器OS时间；真实时钟测试库与演练库不互灌。

核对钱包可用／冻结／总额、逐笔流水、原始票数、唯一香客、幂等结果、整数派彩、本人回执、Token余量和日周月原始计数；做并发最后一炷、封盘后拒绝、响应不确定重试与已封档案指纹检查。独立算法差异为0，重启后无重复扣款／派彩／赠香。核账失败即不进入迁移决策。

候选测试通过只证明候选在独立环境的结果；不能说真实生产账本已迁移或候选已正式发布。

## 6. 同版恢复预演

只在新机网络和容量结果可接受后准备恢复预演：

1. 盘点原服务、真实VERSION、环境键名、systemd／timer／cron、代理、库schema、案例排期、广播、身份／入梁券及备份去向。敏感值只进受限迁移包，不进报告、终端输出或Git。
2. 用SQLite在线备份API取得一致性副本，记录打点时间、SHA256、schema和业务审计。原备份文件及其保留策略不覆盖；新增副本单独命名。运行中的WAL库禁止只复制主sqlite文件。
3. 在新机隔离目录恢复副本并只读核对完整性、外键、身份、香火、投票、历史、排期与广播；候选库和生产副本保持分离。
4. 旧代码／配置／一致数据库作为成套恢复点；首次新机启动用源生产同版构建，不升级schema。系统库与Node在新机重新安装，不整包复制旧OS库或用户node_modules。
5. 新机使用新的SSH主机密钥，不复制旧机SSH私钥；部署客户端的私钥不离开客户端。TLS和必要应用身份分别受控处理，验证新机不会自动注册为另一套公共账本。

在线备份方法以[SQLite官方Backup API](https://sqlite.org/backup.html)为依据。预演完成只能报告“副本可恢复”，不能报告“最终数据已同步”；主服此时仍持续产生新记录。

## 7. 用户决定后才执行切换

切换前提供完整的新机网络、200容量、结算、恢复预演和预算报告，再等待用户决定。现在不改DNS／TTL，也不冻结主服。

真正切换需要短暂冻结业务写入；SQLite单写方案不承诺无感零停顿。演练后报告预计时间，预先准备失败撤回路径，避免跨封盘／午夜等业务边界：

1. 确认新旧生产版本和schema一致；准备新机TLS、访问控制、旧IP转发与独立新备份；记录DNS旧值和缓存TTL。
2. 在切换窗口暂时阻止新业务请求，保留可读的维护响应；停止旧机全部业务写入者，包括后台业务timer／CLI。正常完成在途事务，不强杀数据库进程。
3. 取得最终一致性快照，传入新机、校验并恢复。记录最后请求／票据及审计摘要，确保旧库已静止。
4. 新机恢复同版生产数据，旧机生产后台继续停止，始终只有一套数据库接受业务写入。先验证维护状态下的健康与只读审计，再开放新机。
5. DNS传播期间旧IP的入口只安全转发到新机，不能启动旧账本继续接写。保留Host／签名路径语义；只信任明确的旧代理，不能无条件相信任意X-Forwarded-For或破坏原鉴权限额。
6. 切公共DNS并记录时间。观察旧IP残留、客户端自动重连、未知回执、钱包／票数、账本和新机备份；历史查询与新数据保持一致。
7. 旧机和原备份继续保留，不自动释放。新生产数据另建独立备份计划并完成恢复抽查，不能把旧机的停更备份冒充新主服备份。

## 8. 回退按是否已接收新写入区分

| 时点 | 回退方法 |
| --- | --- |
| 新机尚未接受业务写入 | 撤销新入口／恢复DNS，恢复旧同版服务；确认不存在第二个写入节点 |
| 新机已接受业务写入 | 先冻结新机全部写入，取得最新一致库；恢复到旧机的同版兼容代码，审计后才反向切流。不能仅改DNS使用旧快照 |
| 以后另行升级过生产schema | 先核对旧机是否有兼容代码；未验证兼容时保持维护状态，不让旧1.2直接读取新钱包库，也不丢弃新账回退旧快照 |

回退保护的是已经确认的账务；禁止合并两边各自接收过写入的SQLite库。若新机故障到无法取回最新已写数据，不声称可无损秒回退，应保全节点、报告最后恢复点与未确认意图，再决定恢复路径。

## 9. 每阶段交付

- 准备：新目标清单、原环境保护基线、精确代码／包校验值、独立数据与路由清单。
- 验收：网络与两来源0–200曲线、持续段和重连、功能问题、性能瓶颈、网卡流量与账本核对；400另列。
- 切换决定：同版恢复回执、最终同步办法、单写保障、预期短暂停顿和有新写入后的回退步骤。
- 收尾：原服务启动时间／版本／配置与静态原备份指纹按阶段核对；不对仍在正常变化的生产库要求哈希恒等。业务记录增长、日志增长和正常证书续期单独解释。
